# 모듈 설계

상태: P1/P2 모듈·결과 계약 구현. 상태 해석 변경·근거 추적은 제안. 2026-11-15 (KST), 기준 `11c6ec5` 이후 작업 트리.

목표는 장면 검사와 벤치마크를 유지하면서, 모델 응답·물리 판정·평가를 각각 검증할 수 있게 하는 것이다. 작업 순서는 [실행 계획](plan.md), 지표 정의는 [평가 명세](evaluation.md)를 따른다.

## 분리 전 구조와 문제 (`11c6ec5`)

- `scenes.py`는 입력 로딩·항목 확장·정답 사건 검증을 담당한다.
- `prompts.py`는 프롬프트·모델 출력 스키마와 사건 변환을 함께 담당한다.
- `rules.py`는 사건으로 장면 상태를 갱신하고 위반을 반환한다. 본문은 읽지 않는다.
- `runner.py`는 실행·캐시·추출 변환·규칙 호출·채점·출력을 모두 담당한다.
- `backends.py`는 공급자 호출을 담당하며, `hand-check/`는 종료된 v1 실험이다.

분리의 첫 대상은 `runner.py`의 평가와 저장 결과 분석이다. 기존 파일 전체를 일괄 재배치하거나 서비스·데이터베이스를 도입할 필요는 없다.

## 구현된 책임 경계

아래 모듈은 현재 구현되어 있다. 원본 추출의 완전성 검증을 실행과 분석이 공유하도록 `extraction.py`도 함께 분리했다.

| 모듈 | 입력 → 출력 | 책임과 제약 |
|---|---|---|
| `scenes.py` | 장면 파일 → 장면·평가 항목 | 기존 로딩·확장·정답 검증 유지. 실행 결과와 결합할 때 데이터 식별 정보 제공 |
| `prompts.py` | 항목·조건 → 요청·출력 스키마 | A/B/C/D 입력 계약 유지. gold 사건을 모델 입력에 넣지 않음 |
| `backends.py` | 요청 → 응답·사용량 | 공급자 호출만 담당. 물리 모순이나 평가 점수를 판단하지 않음 |
| `extraction.py` | 구조화 응답 → 정규화 사건·형식 오류 | 사건 변환과 형식 검증. 누락·중복 문장과 잘못된 필드를 검증하며 정답을 보고 보정하지 않음 |
| `rules.py` | 시작 상태·사건열 → 상태열·규칙 위반 | 결정적 판정. 모델·파일·네트워크에 의존하지 않음 |
| `evaluation.py` | 정답·검사 결과 → 지표 | 순수 채점과 구간 계산. 규칙 재실행이나 모델 호출을 하지 않음 |
| `analysis.py` | 저장 보고서·명시적 데이터/캐시 → 새 분석 보고서 | 기존 결과 호환 읽기, 재채점, 원인 분석용 항목 목록. 네트워크 호출 금지 |
| `runner.py` | 실행 옵션·항목 → 실행 보고서 | 요청·캐시·판정·채점을 조합. 검증되지 않은 신뢰도 점수를 확률로 표시하지 않음 |
| `__main__.py` | CLI 인수 → 실행/분석 작업 | `validate`, `run`, `rescore`, `audit` 명령 제공 |

의존성은 `CLI → runner/analysis → prompts/extraction/rules/evaluation` 방향이다. `evaluation`은 기존 필드 또는 새 결과를 정규화해 채점하며, `analysis`의 오프라인 경로는 백엔드를 생성하거나 자격증명을 읽지 않는다. 공통 데이터 계약을 위해 당장 별도 프레임워크나 클래스 계층을 만들지 않는다.

## 조건별 흐름

| 조건 | 흐름 |
|---|---|
| A | 본문 → 모델 직접 판정 → 결과 정규화 → 평가 |
| B | 본문·제공된 시작 상태 → 모델 직접 판정 → 결과 정규화 → 평가 |
| C | 본문·시작 상태·인물·물건 목록 → 사건 추출 → 규칙 판정 → 평가 |
| D | 본문·인물 목록 → 사건 추출 → 미지 시작 상태에서 규칙 판정 → 평가 |

A를 실제 입력에 가장 가까운 기준선으로 유지한다. B의 시작 상태가 별도 모델의 산출물이라면 그 추출 오류·시간·비용도 전체 검사에 포함한다. C와 D는 추출·상태 추적의 병목을 진단하는 비교 조건으로 유지한다. 기존 조건 이름의 뜻을 바꾸지 않는다.

## 검사 결과 계약

실행 성공 여부와 본문에 대한 판정을 두 축으로 저장한다. 아래 필드를 구현했고 호환용 `has_error`, `sentences` 등 기존 필드도 유지한다. `undetermined`는 평가기에서 처리하며 현재 모델 프롬프트가 생성하는 값은 아니다.

| 필드 | 값 | 의미 |
|---|---|---|
| `status` | `ok`, `call_error`, `invalid_output` | 호출 및 결과 검증 상태 |
| `verdict` | `error`, `no_error`, `undetermined`, `null` | 검사 판정. 실패이면 `null`, 성공했으나 판단할 정보가 부족하면 `undetermined` |
| `warnings` | 문장·규칙·이유·근거 목록 | 모델 또는 규칙이 낸 경고. 실패/판단 보류에서는 확정 경고로 채점하지 않음 |
| `issues` | 처리 문제 목록 | 호출 실패, 형식 문제, 상태 계산 한계 등 |
| `provenance` | 실행·응답·버전 식별 정보 | 어떤 입력과 구현에서 나온 결과인지 추적 |

각 경고는 `sentence`, `rule`, `reason`, `evidence`를 가진다. 현재 C/D는 규칙의 문장별 이유를 보존하지만 `evidence`는 빈 배열이다. A/B와 과거 응답은 문장별 규칙/이유가 없어 `null`로 둔다. 후속 근거 추적에서는 이전 문장, 현재 문장, 제공된 시작 상태 중 출처를 표시한다. 자유 서술 `reason`을 자동으로 검증된 근거로 취급하지 않는다.

기존 응답은 항목 전체에 `rule`과 `reason` 하나만 담을 수 있다. 호환 읽기는 원문을 보존하고, 여러 문장 각각에 규칙·근거가 있었다고 만들어내지 않는다. 새 모델 출력 스키마와 기존 캐시 호환 처리는 별도 작업이며, 평가 분리 단계에서는 프롬프트를 바꾸지 않는다.

`no_error`는 지원하는 규칙과 주어진 근거에서 모순을 찾지 못했다는 뜻이다. 알려지지 않은 상태가 하나 있다고 항목 전체를 보류하지는 않는다. 명시적인 처리 한계로 필요한 판정을 수행할 수 없을 때 `undetermined`를 사용한다.

추출 응답에 중복·누락 문장, 범위 밖 인덱스, 필수 정보 없는 사건이 있으면 `invalid_output`으로 기록한다. 유효한 일부 사건의 추적 결과는 진단용으로 보존할 수 있지만, 완성된 검사 결과와 섞지 않는다. 사건이 없는 문장을 명시적으로 빈 목록으로 준 것은 유효하다.

## 상태 해석 설계 — 미구현

아래는 상태 해석의 목표 계약이다. 구현 순서, 변경 대상, 최소 재현과 대조 사례, 전후 비교 절차는 [P3 상세 계획](plans/p3-state-rules.md)을 따른다. 명시적 손 관측을 보존하는 수정과 미확정 손을 표현하는 변경을 별도 묶음으로 진행한다.

### 손의 미확정 상태

현재 `hand=any`는 가능한 손 중 오른손을 먼저 배정한다. 이 때문에 빈손에서 시작한 “컵을 들었다 → 오른손으로 열쇠를 집었다”에 헛경보가 생긴다.

제안은 손이 불명확한 점유를 확정된 좌우 점유와 구분하는 것이다. 가능한 배정은 동일 인물의 손 두 칸에 대한 제약으로 유지하고, 이후 명시된 동작으로 좁힌다. 컵 점유를 지우거나 명시되지 않은 손 바꾸기 행동을 삽입하지 않는다.

| 사건열 | 기대 판정 |
|---|---|
| 컵을 들었다 → 오른손으로 열쇠를 집었다 | 컵이 왼손일 수 있으므로 모순 아님 |
| 오른손으로 컵을 들었다 → 오른손으로 열쇠를 집었다 | 놓거나 옮긴 근거가 없으므로 모순 |
| 컵을 들었다 → 두 빈손이 필요한 행동 | 컵이 어느 손이든 한 손은 차 있으므로 모순 |
| 양손 상태를 모름 → 오른손으로 열쇠를 집었다 | 미지 상태만으로 모순 판정하지 않음 |

판정은 표현된 모든 가능한 배정이 충돌할 때 확정한다. 전체 장면의 모든 조합을 무제한 복제하는 구현은 피한다. 건네기·양손 점유·접촉과 결합했을 때 제약을 유지할 수 없는 경우에는 처리 한계를 기록한다. 자료구조와 지원 범위는 회귀 사례를 먼저 정한 뒤 구현 단계에서 결정한다.

### 물체와 장소의 동일성

부분 문자열 또는 공통 인명만으로 동일하다고 확정하지 않는다. 첫 변경은 공백 정규화 후 정확한 이름과 명시된 별칭을 기준으로 한다. 데이터 전체에 불투명 ID를 도입하는 마이그레이션은 첫 수정의 필수 조건이 아니다.

- `칼`과 `칼집`은 서로 다른 물체다.
- `민준 왼쪽 주머니`와 `민준 오른쪽 주머니`는 서로 다른 장소다.
- `바지 주머니`와 `민준 바지 앞주머니`는 정보가 덜 구체적인 관계일 수 있다. 이름이 다르다는 이유만으로 장소 불일치를 확정하지 않는다.
- 장소 비교는 `같음 / 다름 / 미확정`을 구분한다. 명시적 좌우·소유자 충돌 또는 검증된 장소 식별 정보가 있을 때 다름을 확정한다.
- 별칭 연결 자체가 틀릴 수 있으므로, 별칭의 근거를 검토하고 테스트로 보호한다.

### 상태 근거와 실패 이후

명시된 관측과 엔진의 임의 선택을 구분한다. 경고는 위반 문장과 충돌을 만든 이전 상태의 근거를 추적할 수 있어야 한다. 현재 `cause` 정답 필드는 평가용이며, 예측 경고의 근거를 만들 때 가져다 쓰지 않는다.

현재 `failed`, `loose`, `let_go`, `pairs`도 이후 판정에 영향을 준다. 상태 재생·저장 기능을 확장할 때 이 보조 상태를 빠뜨리지 않도록 검토한다. 모든 보조 상태를 공개 장면 형식에 추가하는 것은 별도 결정이다.

## 결과 보존과 호환성

- 입력 장면 형식 v2와 기존 실행 파일을 읽을 수 있어야 한다. 새 결과 계약에는 별도 `report_version`과 `metrics_version`을 둔다.
- 원본 실행 결과와 캐시를 덮어쓰지 않는다. 재채점과 재실행은 원본 파일의 해시·이름을 참조하는 별도 결과로 남긴다.
- 새 실행에는 데이터·프롬프트·출력 스키마·규칙 구현의 식별 정보, 요청 모델과 실제 응답 모델, trial, 요청 설정을 기록한다.
- 기존 결과에 없는 버전은 현재 버전으로 채워 넣지 않고 `unknown`으로 둔다. 작업 트리에 변경이 있으면 Git 커밋만으로 구현을 식별하지 않는다.
- 현재 Gemini의 `effort` 옵션은 요청에 전달되지 않는다. 요청 옵션과 실제 적용 옵션을 구별하며, 모델 간 같은 추론 예산이라고 주장하지 않는다.
- SDK 키·인증 파일 내용은 보고서와 문서에 넣지 않는다.

## 이번 설계의 범위

평가·추출 검증 분리와 오프라인 분석을 구현했다. 상태 표현 수정, 엄격한 상태 지표, 근거 추적은 원인 분석 이후 순차 진행한다. JEPA 학습, 3D 시뮬레이션, 장면 밖 기억, Canon 연결은 이 단계의 완료 조건에 포함하지 않는다.


현재 새 보고서는 `report_version=3`, `metrics_version=2`, `legacy_metrics_version=1`을 기록한다. `conditions.<조건>.metrics`가 새 지표이고 `legacy_metrics`가 기존 공식이다. 파일명 `run-v2-*`의 v2는 기존 실행 명명 규칙으로 유지하며 지표 버전이 아니다. 데이터 파일과 Python 모듈별 SHA-256으로 미커밋 코드와 프롬프트/스키마를 식별하고, 각 예측에는 캐시 파일의 해시와 캐시 적중 여부를 기록한다.
